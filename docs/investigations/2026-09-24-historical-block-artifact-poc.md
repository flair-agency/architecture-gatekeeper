# Historical CI `BLOCK` artifact feasibility (Issue #20 / #78)

Status: investigation only. This document and `scripts/probe-historical-block-metadata.mjs` do not define an accepted evidence route or alter `Architecture Gate / accept`.

## Finding

GitHub Actions can retain a candidate ReviewRecord from a completed CI `BLOCK` for later inspection. The REST API can retrieve a specific workflow run attempt and its jobs, and it can list artifacts associated with the run. The artifact response includes an artifact ID, an archive digest, repository ID, run ID, and workflow-trigger SHA. It does **not** identify the attempt or job that uploaded the artifact. Therefore, a run-linked ZIP and a JSON file that *claims* `BLOCK` are insufficient by themselves to authenticate the producer. This gap needs a protected producer design and an explicit attestation/verification decision before historical `BLOCK` can be used by the owner-amendment route.

The current CI has no standalone ReviewRecord artifact. The review job emits a validated decision as a same-run output; the report job computes a decision digest and a human-readable comment; the accept job requires `PASS` for enforced mode. A historical run with `BLOCK` normally has a successful review job and a failed accept job. Requiring overall run success would therefore reject the evidence that #78 needs.

## Metadata probe

Run `node scripts/probe-historical-block-metadata.mjs OWNER/REPO RUN_ID ATTEMPT ARTIFACT_NAME` with `GITHUB_TOKEN` set for a private repository. It reads the run, selected attempt, jobs in that attempt, and named run artifact. It rejects mismatched repository/run/trigger SHA, an incomplete attempt, missing or ambiguous artifacts, absent archive digest, and truncated API pages. It returns `METADATA_CANDIDATE_ONLY` and an explicit list of unresolved checks. It does not download the ZIP, parse a ReviewRecord, infer `BLOCK` from a failed run, or issue an acceptance verdict. The artifact name is supplied by the investigator; a future protected producer should incorporate the run ID and `github.run_attempt` to avoid collisions across reruns.

The workflow-run `head_sha` for `pull_request_target` identifies the workflow trigger revision, not necessarily the reviewed PR merge or head. The ReviewRecord must independently contain the reviewed base, PR head and merge revision captured by the trusted review path. A later verifier must compare those fields with current GitHub PR/base state and protected input identities. The probe deliberately labels the API field `workflowTriggerSha`.

Live API spot check on 2026-09-24: [PR #81 run 36004069195](https://github.com/flair-agency/architecture-gatekeeper/actions/runs/36004069195) reported attempt 1 as completed/cancelled, and the attempt-specific jobs endpoint showed its review job as cancelled. The run-level artifact endpoint returned zero artifacts. This confirms that these endpoints are readable for this repository and correctly yields **no historical `BLOCK` candidate** for that attempt; it does not exercise a real ReviewRecord artifact.

## Minimal producer and verifier shape for a later PR

1. In a protected, credential-bearing workflow, emit a versioned ReviewRecord only after the review job completed successfully, the consumer schema and deterministic checks passed, and the validated top-level decision is exactly `BLOCK`. Record the exact decision and digest, repository ID/name, PR number, protected base SHA, PR head SHA, reviewed merge SHA, Gatekeeper runtime SHA, workflow/run/attempt identity, and protected authority/prompt/schema/validation-policy identities. A failed or incomplete model run emits no `BLOCK` record.
2. Upload a single bounded JSON file under a run-and-attempt-specific artifact name. Preserve the upload action's artifact ID/digest. The digest authenticates the downloaded archive bytes against GitHub's artifact metadata; the ReviewRecord should also have a defined canonical byte/digest rule for the JSON itself. These are byte-identity checks, not proof of which job created the bytes.
3. A later protected verifier fetches by exact repository/run/attempt/artifact ID, checks the downloaded archive digest and bounded single-file contents, validates the ReviewRecord and decision against the historical protected inputs, and verifies the selected attempt's workflow and successful producer/review job state. The trusted workflow definition, action dependencies, and every job capable of writing that run's artifacts must be assessed. Run-level artifact metadata alone cannot attest that the intended report job uploaded the bytes. An isolated trusted producer run or a suitably verified GitHub artifact attestation may be required; this choice belongs in the owner-reviewed Issue #20 evidence contract.
4. For Change B, compare the historical `BLOCK` identity to the annotated tag and AmendmentRecord, then check current B/base/head/authority state and the strict authority-only scope under the **previous protected-base policy**. Re-evaluate freshness when relevant bound state changes. This would be a separate protected verification path; it does not turn A's `BLOCK` into `PASS`.

The G0 annotated-tag check is separate from producer provenance. G0 verifies tag content and object/revision identity but makes no claim about the tag actor. G1 owner-principal authentication is a later, independent mechanism and cannot be inferred from an artifact uploader, workflow actor, tagger name, or `triggering_actor`.

## Candidate producer provenance: GitHub artifact attestation

GitHub's artifact attestation is a candidate for closing the uploader gap, separate from the run artifact metadata. GitHub documents verification of an attested file against a particular signer workflow, including a reusable workflow. Its Actions OIDC claims include `run_id`, `run_attempt`, `check_run_id`, `workflow_sha`, and `job_workflow_sha`. A future PoC should attest the exact ReviewRecord bytes in a protected job, verify the subject digest, and determine which workflow/run/attempt/job claims the resulting statement actually exposes to a verifier. Any claim absent from that verified statement needs another trusted binding or must remain unproven. The experiment must also prove that only validated `BLOCK` output can reach that producer job; a valid attestation of arbitrary bytes is insufficient.

This is not yet the selected evidence route. GitHub currently makes artifact attestations available for public repositories on Free, Pro, and Team plans, but private/internal repositories require Enterprise Cloud. The first-user repository is public, so a bounded live experiment is possible here; a general consumer route must either declare that hosting/plan limit or use another trusted provenance mechanism. Neither artifact metadata nor an unverified `run_attempt` string inside the JSON may be promoted to producer authentication.

## Open risks and next validation

- An artifact is associated with a **run**, while reruns share the run ID. A name or embedded `run_attempt` can distinguish candidate bytes operationally but does not alone prove the uploader's attempt. A partial rerun can also leave jobs and artifacts from earlier attempts in the same run. The verifier must select an exact attempt and reject ambiguous or inconsistent provenance.
- Artifacts expire or can be deleted. If a historical `BLOCK` must outlive Actions retention, the owner must select a durable, independently verifiable archive or a re-review process; absence of evidence fails closed.
- The archive digest is for the ZIP transport. Validate it separately from the JSON record digest and reject duplicate names, extra files, path traversal, oversized files, and malformed JSON when extraction is implemented.
- This branch has no upload workflow and no production verifier, so it cannot run an end-to-end live artifact test. The next safe exercise is a manual-only trusted producer on a test PR, followed by a read-only API/ZIP probe over a real `BLOCK` and a rerun. The current acceptance workflow remains unchanged during that test.
