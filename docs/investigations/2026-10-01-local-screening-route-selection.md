# Local screening route selection (provisional, 2026-10-01)

## Status

This is the #242 route-selection input for Issues [#240](https://github.com/flair-agency/architecture-gatekeeper/issues/240), [#241](https://github.com/flair-agency/architecture-gatekeeper/issues/241), [#242](https://github.com/flair-agency/architecture-gatekeeper/issues/242), [#243](https://github.com/flair-agency/architecture-gatekeeper/issues/243), and [#244](https://github.com/flair-agency/architecture-gatekeeper/issues/244). It recommends a bounded design for #243; it does not install or enable a consumer route. In the #241 CLI probe, a hook returned a random nonce after 1.203 seconds and the active turn quoted it; the triggering action showed no wait. In a second trial, a 9-second hook overlapped a 2-second shell command, but the main turn ended before hook completion and its follow-up reported no result. On the next submitted turn, the model quoted the completed hook's nonce. The session did not wake or start a turn while idle. ## Existing contract

The normative contract remains [`architecture.md`](../architecture.md). Local review is development feedback intended to identify responsibility and trust-boundary problems before code is pushed. Review execution, evidence, and protected acceptance remain distinct. Local adapters share the revision-bound request and deterministic decision-validation contract, while using host-appropriate reviewer transports. `PASS`, `BLOCK`, and `OWNER_DECISION` retain their existing meanings. A reviewer refusal, cancellation, unavailable configured model or effort, transport failure, or invalid response leaves the review incomplete.

This investigation proposes no new assurance rule or owner decision. The local screening role is already in the canonical contract. The priority that this screening must not stall productive work is the user's constraint recorded in Issue #240 and governs this route evaluation.

## Recommended bounded design for #243

Implement an **opt-in, CLI-only PostToolUse change-screening adapter**. The hook does a cheap local change check after supported file-capable tool events and starts semantic review only when the candidate input changed. This avoids a model call for every user prompt, begins after actual edits, and leaves design-intent review to the existing explicit native Skill. It is a best-effort change screen; it does not claim to ensure that every design decision or every edit is screened before work continues.

Use the documented [Codex Hooks](https://learn.chatgpt.com/docs/hooks) PostToolUse fields `session_id`, `cwd`, `hook_event_name`, `turn_id`, `tool_name`, `tool_use_id`, `tool_input`, and `tool_response`. The consumer's opt-in `hooks.json` should match `Bash`, `exec_command`, `apply_patch`, `Edit`, and `Write` with `async: true`; Codex documents that unified exec may be reported canonically as `Bash`. Add consumer-specific editor/MCP tool names later if dogfooding shows they are needed. The command must validate `PostToolUse` input and must not depend on the unstable transcript format.

At each eligible event, wait a deterministic two-second batching delay from the first event, then capture `git diff --binary --no-ext-diff --no-color HEAD`, which covers staged and unstaged changes to tracked paths. Later events update the latest marker but do not extend the active invocation's delay. Read `HEAD` before and after snapshot creation; if it moves, return `incomplete` rather than pairing the patch with the wrong authority revision. Pass the actual bounded patch bytes in the existing review request's task text, explicitly labeled untrusted candidate evidence. Do not include event/tool IDs or arbitrary shell command text/output in the semantic task input: event IDs are output metadata, and tool details may contain secrets or irrelevant content. Use a fixed 64 KiB patch cap for this pilot. If the patch exceeds the cap, there are untracked non-ignored paths, a dirty submodule, or a snapshot cannot be read consistently, emit `incomplete` without a semantic decision; list only bounded path/status details. This is an explicit pilot coverage limit, not a `PASS` for the omitted content. Do not inspect ignored files or feed the previous prompt-hook decision into this review. The reviewer still receives repository authority, prompt, schema, model and effort through the existing revision-bound builder and response validator; the patch remains untrusted task context.

Use a deterministic identity derived from the candidate patch bytes, `HEAD`, and the committed configuration, authority, schema, prompt, reviewer model and effort. Do not include `tool_name`, `tool_use_id`, turn ID, or session ID in semantic request identity; expose these only as output metadata. Keep one active reviewer per worktree and a single replaceable latest-change marker under that worktree's Git metadata, not a history of results. Store coordination files with private permissions. Events during a review only replace/dirty that marker and return; do not start another reviewer or drain the marker from the active invocation. The active invocation claims only the marker file observed before capture; later markers remain untouched. After the active lock is released, the next eligible matching PostToolUse event waits its fixed two-second batch delay, captures the then-current diff, and starts one review for that latest change. No background daemon, unbounded queue, hidden catch-up reviewer, repeated prompt model call, durable result registry or review attestation is needed. A dead active reviewer lock is reclaimed only after checking its owner PID. If the tiny stale-recovery guard itself is left by a killed process, the adapter fails incomplete and reports its Git-metadata path for manual cleanup rather than risking a second reviewer. A host that cancels a process at session end can discard its output without a callback; that remains an unscreened case, not a semantic decision.

Emit only valid informational PostToolUse JSON: `hookSpecificOutput.hookEventName = "PostToolUse"` and concise `additionalContext` containing the status (`PASS`, `BLOCK`, `OWNER_DECISION`, or `incomplete`), summary, reviewed revision, and request/snapshot identity; event IDs may appear as metadata outside the decision task. For `BLOCK`, `OWNER_DECISION`, and `incomplete`, also use `systemMessage` as a short visible warning. Never return `decision: "block"`, `continue: false`, or exit status 2: the tool has already run, and this screening must not alter or reject its result. Transport errors, timeout, model/effort unavailability, malformed output, unsupported snapshot, and cancellation are `incomplete`, never semantic decisions. Cap the serialized output at 4,000 UTF-8 bytes, truncating only the summary while retaining status, revision, request/snapshot identity and event metadata. Preserve the current synchronous `runHookCli`, `runHook`, and manual CLI behavior exactly; the new adapter is additive and opt-in.

Keep #243 to these package-owned files:

- `src/local-post-tool-screen.mjs`: implement the PostToolUse adapter, bounded tracked-diff snapshot, candidate identity, and minimal private per-worktree lock/latest marker; reuse existing request construction, read-only reviewer transport and deterministic validation.
- `test/local-post-tool-screen.test.mjs`: use the existing isolated Git/mock-Codex fixture pattern to verify staged and unstaged tracked patch bytes reach the request; unchanged patch skips model invocation; request identity changes when candidate patch, `HEAD`, or committed reviewer inputs change but not when only event IDs/tool names change; untracked/oversize/dirty-submodule/snapshot failures report incomplete; bursts debounce; one active run prevents a second; changed candidates replace the latest marker and run only on the next eligible event; all three decisions and reviewer failures produce valid informational output without block/continue semantics; serialized output remains under 4,000 UTF-8 bytes with mandatory identities preserved.
- `test/installed-smoke.mjs`: exercise the additive exported API through the installed package while retaining the existing synchronous Hook smoke assertions. The current release workflow already invokes installed smoke.
- `README.md` and `docs/integration-reference.md`: document the opt-in launcher and `PostToolUse` `async: true` snippet, covered tool names and snapshot limits, required project/hook trust, non-blocking informational behavior, and the fact that no consumer is enabled by default.

Do not add a new package binary, edit this repository's `.codex/hooks.json`, or change `package.json` unless the implementation demonstrates that the additive exported launcher cannot be used. The package root already exports `src/local-gate.mjs`, and the consumer owns its hook configuration. Focused tests must confirm the current synchronous route's behavior still passes. Then #244 should dogfood an actual structured reviewer result and measure changed-snapshot frequency, reviewer cost, time-to-result, how often feedback arrives before the task moves on, skipped/untracked coverage and single-flight stale-result behavior.

## Desktop and rollout boundary

The #233 evidence establishes CLI behavior only. It does not establish Codex desktop hook loading, project-trust review, or result delivery. The available app-server protocol exposed lifecycle notifications and Skill enumeration but no dedicated hook-run or model-free Skill-dispatch request. Do not market or enable this CLI pilot as solving a desktop workflow.

Desktop capability can be checked without global configuration changes or a new user-owned chat only if an already-existing desktop thread is operating in a suitable already-trusted isolated project. In that thread, a temporary project-local synthetic `PostToolUse` hook can return a random nonce after a fixed delay; verify tool progress plus delivery at the active-turn or next-user-turn safe point, then deactivate the exact handler and remove the fixture. If no such existing trusted thread/project is available, keep desktop support unresolved; do not broaden global trust or create a chat for this probe. Desktop E2E, if safely available, is a separate verification stage from #243 and belongs with #244.
