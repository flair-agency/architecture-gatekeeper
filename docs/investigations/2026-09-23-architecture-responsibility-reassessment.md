# Architecture Gatekeeper responsibility reassessment

Assessment date: 2026-09-23 (UTC); decision update: 2026-09-24 (UTC). Status: **native Codex Code Review is advisory; required-Gate delegation to it is not an active experiment. The smaller Gatekeeper boundary remains under assessment.**

This report addresses [Issue #50](https://github.com/flair-agency/architecture-gatekeeper/issues/50), including the distributed-authority requirement in [#51](https://github.com/flair-agency/architecture-gatekeeper/issues/51). The implementation baseline is Gatekeeper main `bf11b061ece6551991f234b528ad955fdd7623be`. The inspected local checkout `50d4d0c6a9613185b514da4cda6341cb92d8e6a3` differs from that baseline only by the unadopted #45 investigation document; that document is not treated as implemented behavior or adopted authority.

This is a recommendation, not an amendment to `docs/architecture.md`, permission to disable a required check, a decision on Provider PR #29, or a claim that all #50 acceptance criteria have been met. The initial assessment used documentation and historical observations; the paired native input probes below add four live GitHub Code Review observations. This update changes how those observations guide the product boundary; it does not change their recorded results.

## Recommendation

**Treat GitHub Codex Code Review as an advisory reviewer. Stop experiments aimed at delegating the required Gate's semantic execution to that surface while it has no supported authority-input and result contract.** OpenAI describes Code Review as an additional reviewer and says tests, branch protections, and required approvals provide hard enforcement ([custom review rules](https://developers.openai.com/blog/custom-code-review-rules-for-codex)). Its observed ability to identify architectural defects means architecture reasoning is not unique to Gatekeeper; it does not make the native review an acceptance interface.

The publicly documented GitHub Code Review interface does not establish a supported way to inject a complete protected Authority Set and receive a structured, complete decision bound to that set and the reviewed revision. This is a statement about the documented contract reviewed for this assessment, not proof that no private, account-specific, or future interface exists. Behavioral probes cannot substitute for such a contract. Do not convert a comment, an empty finding list, a completion summary, or a thumbs-up into `PASS`.

For an automated required Gate, retain Codex semantic execution through the supported Codex Action / `codex exec` path. OpenAI documents `codex exec` for scripts and CI jobs that need a bounded workflow and structured output ([Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)); its skills-evaluation guidance shows using captured runs, deterministic checks, rubric grading, and `--output-schema` for repeatable evaluation ([Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)). These interfaces make the execution boundary programmatic; they do not guarantee semantic correctness, authority consumption, or acceptance. Gatekeeper still owns the protected input selection, validation, evidence identity, and required-check decision.

“Thin” therefore describes the surrounding custom mechanisms, assessed one responsibility at a time. Keep the consumer-declared Authority Set and its protected revision selection/materialization (including the unresolved #51 completeness work), the prompt/schema contract, the Codex Action invocation, deterministic decision validation, the evidence needed to bind the result to the run and reviewed state, and protected acceptance enforcement. The normative contract also makes local/manual review a first-class, independently usable development path. Its stages serve different moments: explicit manual review supports design-time decisions, automatic local feedback supports implementation-time correction, and CI supplies pre-merge independent enforcement. These capabilities are not deletion candidates under the current contract. Their adapters may be replaced, including the current command Hook, if the replacement preserves the required workflow capability; removing a capability requires an explicit owner contract change. Hook-specific maintenance cost has not been measured, so cost alone is not evidence for removing it. Assess duplicate transports, packaging surfaces, reporting/sticky comments, and optimization or provenance machinery against actual use and contract. Do not thin the semantic executor by delegating it to native Code Review.

The stronger guidance treatment #55 produced no finding for the expected target-contract violation, while safe control #56 also produced no finding. That observation does not identify which inputs native review used, but prevents treating the earlier #53/#54 findings as evidence of robust guidance self-modification resistance.

Retain the present required execution path while evaluating which surrounding mechanisms can be removed. This interim recommendation does not justify every local adapter, packaging route, Action optimization, or future evidence system. The current implementation also has an authority-completeness gap; retention is not a finding that it already satisfies #51.

Retirement remains a valid outcome under an explicit owner decision to use advisory AI plus deterministic controls and human architecture decisions. That changes the assurance contract for current enforced consumers and requires the owner to record the decision in canonical authority. If independent automated architecture acceptance remains mandatory, the recommended candidate is a smaller governance/acceptance shell using Codex Action / `codex exec`; this recommendation does not imply that the current full stack is necessary or that the candidate is already deployable.

## Evidence standard and limitations

- **Documented**: primary product documentation or normative repository contract. OpenAI's current Code Review guidance calls it an additional reviewer and assigns hard enforcement to tests, branch protections, and required approvals. OpenAI documents `codex exec` for bounded script/CI workflows with structured output and describes evals for recording and grading agent behavior. These are supported usage descriptions, not guarantees of semantic correctness or complete review.
- **Observed**: inspected repository source, configuration, API response, or historical review result.
- **Inference**: assessment derived from those facts, not a product guarantee.
- **Untested/unknown**: no verified supported interface or controlled measurement.

The historical examples were not generated under a common protocol. They cannot establish recall, false-positive rate, repeatability, equal-input quality, or comparative cost. Model choice, including Astra, is not evidence of review correctness. Existing unit tests describe deterministic behavior; they cannot establish that a model consulted or correctly interpreted every authority.

### Validation surfaces and proof boundaries

Local and GitHub validation are not interchangeable, but neither does every fixture need to be duplicated on every surface. Each claim should be tested at the lowest surface that can actually establish it, followed by integration checks at the trust boundary it crosses.

| Property | Primary proof surface | What that proof establishes | What it does not establish |
| --- | --- | --- | --- |
| Deterministic authority/governance logic | Local fixture/unit/integration tests | Authority selection, immutable revision resolution, bounded materialization, digests, missing/conflict behavior, and deterministic normalization. | That GitHub supplies the same protected inputs, permissions, event state, or merge policy. |
| Semantic execution for an automated required Gate | The selected supported Codex Action / `codex exec` workflow on fixed inputs, with captured structured result and task-specific eval cases | Whether the configured run starts, receives the intended request, emits schema-conforming output, and meets the measured semantic rubric on the tested fixtures. | Schema conformance or a passing eval set does not prove every authority was consulted or all future defects will be found. |
| Advisory native Code Review | GitHub Codex Code Review on fixed PR revisions | Observed findings, completion behavior, and usefulness as an additional reviewer for those revisions. | It does not establish protected Authority Set ingestion, exhaustive decisions, completion evidence, or required-Gate suitability. Further probes do not fix that contract gap. |
| Acceptance and enforcement | GitHub Actions plus actual required-check/branch-protection/ruleset behavior | Binding to the current head and authority identity, cancellation/skip/service-failure handling, permissions/identity, stale-result rejection, and whether merge is actually blocked. | Local PASS/FAIL behavior or a successful workflow command cannot prove repository merge enforcement. |

Validation should avoid a full Cartesian “local × CI” duplication. Authority resolver edge cases can remain local tests while GitHub CI verifies protected input selection, Codex Action execution, structured-decision validation, and acceptance. Native Code Review can be sampled as advisory feedback, but it is not a semantic replacement candidate. A thin-path candidate still requires a GitHub shadow run and acceptance tests joining the retained pieces.

The Provider contract specifically chooses clean-checkout CI acceptance and no automatic prompt hook, so that consumer-specific choice does not justify requiring a Hook in every consumer. The shared contract separately requires local/manual review as a first-class capability; design-time manual review, implementation-time automatic local feedback, and pre-merge CI have distinct roles. ## Distributed-authority experiment: what must be demonstrated

Source topology is not authority topology. Git submodules are one way to resolve pinned sources, not a mandate to nest every authority under one root. The #51 completeness question remains an active Gatekeeper responsibility; its resolution does not depend on native Code Review.

For Provider #29, construct a bounded, explicitly selected set using the protected Provider architecture at `a27633c` and owner-confirmed immutable revisions of all four adopted external sources. The write contract refinement at `c661e82` is known adopted evidence, but an experiment must still record the exact chosen set and relationship rules. Do not recursively promote every link in those documents to authority. Do not silently choose “parent wins.” The Provider explicitly delegates to its adopted parent contracts; unresolved conflicts beyond that delegation require an owner decision.

The historical native-only route was **materialization without custom semantic execution**. This update closes that as a required-Gate experiment: GitHub Codex Code Review remains advisory unless OpenAI publishes a supported input and result contract that supplies the required assurance. The probes below remain useful observations of advisory behavior and of the limits of inferring authority selection from findings; they do not authorize a required-check adapter.

1. Reopen this investigation only if an official, supported GitHub Code Review interface is documented for supplying a protected, immutable Authority Set and obtaining structured completion/decision evidence bound to the relevant revisions.
2. If such a contract becomes available, verify its documented guarantees first; only then decide whether new fixed-revision probes are justified. Behavioral probes alone cannot establish a product-level I/O guarantee.

The materials reviewed for this assessment describe repository guidance and review requests, but did **not** document a protected Authority Set input contract or a structured, complete result contract for GitHub Code Review. Required-Gate delegation is therefore excluded from the current candidate set. This does not establish that such an interface is impossible or absent from every account; a future supported contract would be new evidence and could reopen the decision.

## Migration, validation and rollback

1. Record consumer assurance needs and the chosen owner decisions in canonical authority. Keep current required checks active throughout the assessment.
2. Prepare a bounded complete Authority Set and fixture corpus for Gatekeeper. Preserve its three distinct stages: design-time manual review, implementation-time automatic local feedback, and pre-merge CI enforcement. Assess transports/adapters (including the command Hook), Skill/package surfaces, reports/comments, and integrity optimizations against consumer workflow and the contract. Replace the Hook adapter only if an equivalent automatic local-feedback path remains; removing that capability requires an explicit owner decision recorded in canonical authority.
